# 审查证据与验证清单

## 本地证据入口

以实际 agent 目录为根，按需读取以下内容。不要遍历输出整个 node_modules。

| 内容 | 常见位置 | 用途 |
| --- | --- | --- |
| 启动入口 | `bin/pi.ps1`、`bin/pi-launcher.js` | 确认实际选择发布版本的方式 |
| Managed 当前版本 | `install/current-version` | 确认启动器选中的版本，不等同于现存进程版本 |
| Pi 包与更新记录 | `install/releases/<version>/node_modules/@earendil-works/pi-coding-agent/package.json`、`CHANGELOG.md` | 版本与升级区间 |
| 官方本地文档 | 同包 `docs/`、`examples/extensions/` | 公开契约、配置和推荐用法 |
| 公开导出与类型 | 相关包的 `package.json` exports、`dist/index.d.ts` 与被导出的声明 | 区分公开 API 和实现细节 |
| 扩展加载器 | coding-agent 的 `dist/core/extensions/loader.js` 及相邻实现 | 核实子路径别名、虚拟模块和真实加载行为 |
| 扩展盘点 | `extensions/AGENTS.md`、实际入口和共享模块 | 当前职责与实现；清单不代替源码 |
| 测试配置 | 本地扩展或已安装包中的 `tests/run.ps1`、可选版本解析脚本和类型配置 | 测试覆盖、参数、所选发布版本和编辑器路径；按实际目录定位 |

相关包通常包括 pi-coding-agent、pi-ai、pi-tui、pi-agent-core、pi-codemode；由实际变化决定检查范围，不假定各包每次都会新增 API。

## 状态检查

1. 读取适用规则及测试入口，确认当前工作目录、系统解释器和必要工具已存在。
2. 记录用户要求的升级区间、实际安装版本、可用旧发布目录、当前代码状态和测试选择逻辑。
3. 如果已有进程版本无法确认，写“未确认”，不要拿安装目录、旧会话日志或新开的 CLI 进程替代证据。
4. 需要检查配置时仅提取与问题有关的非秘密字段，不整份打印 auth、环境变量或供应商配置。
5. 发现并行编辑时保护现有文件，必要时标记结果针对的文件哈希。未获授权不创建 Git 仓库或重置工作区。

## 全量测试

先阅读当前 `tests/run.ps1` 及必要测试初始化，确认离线替身、进程执行、临时写入和清理范围。全量测试并非“绝对只读”：允许现有测试在其约定的隔离目录中写入临时产物；不据此授权真实配置改动、网络访问或历史工具执行。

先读取当前项目或包的测试入口，确认工作目录和参数。对于本分发仓库，从包根目录运行，并显式指定目标 Pi 的已安装包目录：

```powershell
.\tests\run.ps1 -PiPackageDir '目标版本的 @earendil-works/pi-coding-agent 安装目录'
$reviewTestExitCode = $LASTEXITCODE
```

手动维护的本地扩展可能另有无需参数的入口，或支持 `-Tests` 选择测试。按实际脚本使用已有参数，不把本分发命令照搬到所有安装方式，也不假定一定存在 `tsconfig.json` 或版本解析脚本。

立即保存并检查退出码。PowerShell 和原生程序的规则以当前 AGENTS.md 为准；接受的非零值必须是该操作已知且明确处理的结果。

- 记录入口实际选择的 Pi 版本。若它选择“最高可用安装版本”而用户要求的是另一目标，先找既有版本选择方式；没有时如实报告，不悄悄重写测试配置或冒充目标版验证。
- 类型检查失败、缺少解释器或其他前置失败，与测试断言失败分开记录。不自动装依赖或切换运行时让测试“通过”。
- 测试入口可能遇错即停。读取本轮测试列表，识别失败入口和未运行入口。当前入口支持时，可用 `-Tests` 参数继续剩余测试；不要为了运行测试而改原文件。
- 对每个入口分别记通过、失败、跳过、未执行；部分断言成功不等于整个入口通过。失败入口后面的场景仍可能未执行。
- 对测试中的符号链接、WSL、权限、平台条件等跳过项逐项说明。不要把缺少覆盖说成通过。
- 只因代码、环境或新发现的问题改变才重跑相关检查；常规通过后不反复重跑。
- 必要加载检查使用与实际 Pi 一致的加载器和隔离配置。加载通过不等于 session_start、真实模型请求或 GUI 已验证。
- 真实历史会话仅在必要时复制后离线重放，保留原文件哈希，不执行任何历史工具调用。

## 变化到扩展的映射

每项关注变化记录以下字段：

| 字段 | 要回答的问题 |
| --- | --- |
| 触发条件 | 在启动、恢复、重载、工具调用、模型请求还是某个 UI 事件发生？ |
| 原生变化 | 新 API、加载修复、行为修复、默认值变化还是内部重构？ |
| 本地实现 | 哪个扩展入口、共享模块、测试和说明依赖旧行为？ |
| 原始意图 | 用户需求、功能缺口、缺陷补偿、旧版兼容还是未知？依据是什么？ |
| 覆盖差异 | 正常、错误、取消、会话切换、旧会话、非 TUI 等路径是否都覆盖？ |
| 限制与元数据 | 工具显式移除、CLI 排除、opt-in、计费币种、去重、原始快照是否仍正确？ |
| 可导入性 | 符号是否经公开 exports 暴露且能被实际扩展加载器解析？ |
| 结论 | 保留、复用、收缩、候选移除或证据不足，优先级是什么？ |

不要仅因 `.d.ts` 无变化就停止检查运行时；也不要因为发布包包含某个函数就把深层内部路径推荐成稳定扩展 API。

## 失败归因

| 分类 | 证据要求 | 下一步 |
| --- | --- | --- |
| 插件缺陷 | 当前公开契约与用户需求明确，但插件实现违反它们 | 提出功能修复及验证计划 |
| 上游行为变化 / 旧测试预期 | 更新记录与原生复现支持新行为，失败断言依赖旧行为 | 评估收缩补偿与更新断言；保留边界覆盖 |
| 上游疑似回归 | 公开契约、发布说明和实际行为存在冲突 | 给出最小复现、影响与临时方案；标为疑似 |
| 环境限制 | 缺少运行时、权限或平台前提等有直接证据 | 报告未验证范围，不改业务逻辑绕过 |
| 未确定 | 证据不足或存在并行改动等干扰 | 明确待查问题，不以放宽断言掩盖 |

示例：Pi 1.4.0 把恢复旧会话时默认启用的新扩展工具未激活归为修复。本地 Auto 曾补偿这一行为；不能因为补偿和断言已存在，就要求原生继续漏激活工具。还要分别核实历史移除、显式 CLI 选择、defaultActive: false 等限制及本地额外职责。这只是方法示例，未来审查须以当时版本和当前实现重新验证。

## 人工检查与收尾

- 只列出本次受影响的 GUI/交互步骤及预期结果，例如叠加弹窗恢复、全屏焦点通知、手动取消和工具选择；不自动操作真实交互界面。
- 报告应能指导下一步评审：哪些代码可简化、哪些边界保留、哪些测试应调整、哪些仍缺证据。
- 纯审查不要求重新加载插件。Pi 自身升级要重启进程；后续修改扩展后按实际加载机制提醒 `/reload` 或重启。

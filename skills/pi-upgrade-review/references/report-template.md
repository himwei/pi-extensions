# Pi 升级审查报告模板

以下是内容结构，不要求逐字复制所有标题。简短审查可合并段落；没有证据的项目写未确认，不填猜测值。

报告正文同时用于聊天回复与 Markdown 归档。默认在实际 Pi agent 目录的 `docs/pi-upgrade-reviews/` 下按升级区间和 `vN` 创建新文件；保留既有报告，不写入会被包更新替换的安装目录。写明完成时间、旧版/新版和“完成”或“部分完成”，供后续版本监测任务判断基线，避免仅因存在报告就把部分审查当作完成。

## 结论

- 审查区间、基线依据、本地安装版、运行进程版是否确认、测试实际使用版。
- 优先处理的事项，以及本轮是否发现可复用原生能力或可退役补偿。
- 实际做过的检查、未验证部分和本轮有无文件改动。

## 扩展与验证状态

| 检查 | 结果 | 范围 / 限制 |
| --- | --- | --- |
| 扩展盘点与工作区状态 | 待填写 | 以实际清单和源码为准 |
| 类型检查 | 待填写 | 注明所用 Pi 类型版本 |
| 全量测试 | 待填写 | 统计测试入口，不混同为断言数量 |
| 原生加载检查 | 未执行 / 待填写 | 写清隔离方式；不等同于完整运行 |
| 人工交互检查 | 待人工 | 只列本次受影响场景 |

失败、跳过和中止后未运行的项目分别列明。现有全量入口首次失败后，补跑剩余入口的结果也应计入；失败入口未到达的后续场景仍标记未验证。

## 变化与实现的关系

| 上游变化及来源 | 当前扩展 / 模块 | 原生覆盖与剩余差异 | 建议 / 优先级 |
| --- | --- | --- | --- |
| 待填写 | 待填写 | 待填写 | 保留 / 复用 / 收缩 / 候选移除 / 证据不足 |

每项重要结论链接到当前本地源码、更新记录、公开声明或复现证据。建议复用 API 时给出准确符号、公开入口、适用路径与兼容性限制；不要用符号列表代替可行性分析。

## 补偿逻辑复核

每项说明：

1. 原始问题和意图分类，依据何在；来源不明则明确说明。
2. 上游是否已经修复相同问题，适用版本与触发范围。
3. 本地仍承担的用户需求、错误/取消/恢复路径和元数据职责。
4. 保留、收缩或移除的理由、需要保留的回归覆盖及证据置信程度。

## 失败归因与适配建议

明确区分插件缺陷、上游变化、旧测试预期、环境限制和未确定原因。不能仅凭测试失败就修改实现或放宽断言。

对建议的功能修改交付以下评审信息：

- 计划：具体文件、要调整的职责和所复用的原生 API。
- 预期行为变化：触发条件和用户可见结果。
- 范围外副作用 / 兼容性影响：有证据地列出，没有则明确写“无”；用户要求的变化本身不算副作用。
- 替代方案：只列有意义的选择与代价。
- 验证：必要回归、需要人工检查的点、缺少的前提。

## 后续事项

按优先级列出建议，清楚区分已经完成的验证和仅供建议的修改。列出需要用户决定的问题与最小信息；不为可独立完成的本地检查提前中断。

# Pi 升级审查

目标是让本地扩展尽可能依赖 Pi 原生公开 API，并及时移除已经失去必要性的补偿逻辑。默认交付并归档审查报告；除新增报告外，不要在审查中顺手修改扩展、测试、配置或依赖。

这是 Pi 原生技能，执行于调用它的当前会话。需要独立审查会话时，由用户先执行 `/new`，再执行 `/skill:pi-upgrade-review`。外部调度器（例如 Codex 自动化）也可以显式读取本文件并执行相同流程；技能本身不自动开会话、不启动另一个模型进程、不注册升级监听。

## 输入与约束

- 调用示例：`/skill:pi-upgrade-review`、`/skill:pi-upgrade-review 1.3.0 -> 1.4.0`、`/skill:pi-upgrade-review 重点检查工具恢复和计费`。参数是审查范围，不是修改授权。
- 以当前 Pi 实际使用的 agent 目录为准，默认 `~/.pi/agent`；设置了 `PI_CODING_AGENT_DIR` 时使用该目录。优先采用用户提供的目录和实际配置，不照抄历史会话中的版本、状态或结论。除 agent 目录下的 `extensions`，还需识别原生包配置指向的扩展和包根目录；技能自身的安装目录不等同于用户扩展目录。
- 先读取适用的 `AGENTS.md`，尤其是 agent 根目录和 extensions 目录中的规则。后续步骤均服从当前用户授权与本地规则。
- 使用系统或项目已有的 PowerShell 7、Node、TypeScript 和解释器；不安装依赖、不修改依赖文件，不切换到临时或内置运行时补齐环境。
- 默认使用本地更新记录、文档、声明、源码和测试。需要外部资料时，先说明目标页面及缺少的证据，取得访问授权；本地能够完成的部分继续推进。
- 不读取凭据文件或真实密钥。避免将会话正文、工具参数、完整环境变量或配置中的秘密复制到报告。
- 复杂 GUI、终端焦点、弹窗与真实交互由人工验证；AI 只运行现有、适用的离线非交互检查，并列出人工注意点。

## 执行顺序

### 1. 确定版本与审查基线

检查实际启动入口、安装包版本和本地 Changelog；使用 managed install 时再核对 `install/current-version` 及对应发布目录，其他安装方式按实际入口定位。区分已安装版本、当前运行进程版本、测试所选版本和编辑器类型路径。新启动的 `pi --version` 不能证明已有进程的版本。

旧版本优先取用户明确指定或有证据的上次审查版本；其次考虑本地保留的前一版。仅有 Changelog 的相邻条目不能证明用户从该版本升级。报告基线来源与缺失信息，不根据目录名称的字典顺序选择最新版本。跨版本升级要覆盖整个区间。

### 2. 先读 Changelog，再建立变化清单

完整检查区间内的 Added、Changed、Fixed、Breaking Changes 和相关说明。修复旧行为同样可能改变扩展依赖的契约，不能只搜索“新增 API”。每项记录变化、来源位置、可能涉及的扩展和待验证问题。

### 3. 盘点当前扩展与基线状态

读取扩展清单、实际入口、共享模块、测试入口、类型配置与适用文档，核实哪些实现使用公开 API、内部路径、原型/私有字段、自建包装或补偿逻辑。

有 Git 仓库时检查工作区状态；没有时明确说明，并用必要的文件版本或哈希记录审查范围。保留其他会话的改动；关键文件审查期间改变时，重新确认相关证据，不把不同版本的代码结论混在一起。

随后运行现有的全量测试入口及其类型检查，并记录真实退出码和跳过项。执行细节见 `references/review-checklist.md`。测试失败先归因；入口遇错中止时，要在条件允许时用原有选择参数继续检查剩余测试入口，分别记录结果，不能把未执行项算通过。

### 4. 核对公开 API 与实际原生行为

对比相关 Pi 包旧版和新版的公开导出、`.d.ts`、加载器别名及必要实现。验证候选 API 在当前扩展运行环境中是否真正可导入、语义是否匹配，而不只看它出现在某个内部文件里。

区分：新 API、已有 API 的加载修复、原生行为修复、内部实现改动、自动获得的运行时改进。声明文件不变不代表行为不变；声明出现某字段也不保证所有传输或调用路径都支持它。

对可疑行为优先运行现有的隔离 SDK 测试或最小离线复现。禁止为了验证而执行真实历史工具调用、发模型请求、连接供应商、激活真实工具或改动实际配置。导入模块也可能有副作用，加载检查须先确认初始化行为及隔离方式。

### 5. 逐项重新判断补偿逻辑是否仍有必要

每个相关实现先归为：**用户明确需求、原生能力缺口、上游缺陷补偿、兼容旧版本、来源未确认**。用户已经使用或为它编写过测试，不足以证明它是应长期保留的 Pi 功能。

核对 Changelog、官方说明、原生实现和测试证据：上游是否已经修复；修复是否覆盖相同触发条件；原生范围是否比本地补偿更广；用户需求还有哪些剩余差异。不要为保留旧测试而重新制造上游缺陷，也不要仅凭名称相似就删除用户需要的行为。

结论使用：**保留、直接复用原生、收缩补偿、候选移除、证据不足**。对候选移除说明剩余职责、支持版本下限、行为差异及验证要求。只有证据完整时才建议删除；不确定的设计意图标记为待确认，不编造上游动机。

### 6. 给出报告与适配优先级

采用 `references/report-template.md` 的结构，按实际复杂度压缩篇幅。先给结论和需要处理的事项，再展示依据，避免复述整份 Changelog。

列明类型检查、测试、加载检查与人工检查各自的范围和结果。区分插件缺陷、上游行为变化、旧测试预期、环境限制和未确定原因，注明未执行或中止的场景。

提出可具体评审的修改计划、预期行为变化、范围外副作用或兼容性影响（无则写“无”）及有意义的替代方案。审查到此完成；功能修改遵循用户当前审批规则，不把技能调用当作修改授权。后续确实改动代码时提醒重新加载或重启，Pi 自身升级须重启进程。

### 7. 自动归档报告，复用 `/summary` 的保存语义

将本次独立可读的报告正文保存成 UTF-8 Markdown，并在最终回复中给出可点击文件路径。默认目录为实际 Pi agent 目录下的 `docs/pi-upgrade-reviews/`，用户可明确指定其他持久目录；不要把报告写入由包更新替换的安装目录。文件名为 `Pi-upgrade-review-<旧版本>-to-<新版本>-vN.md`，旧版无法确认时使用 `unknown`。选择下一个可用版本号，以新文件方式创建，已有报告不覆盖；发生同名竞争时重新选择名称，不替换另一会话的结果。

这对应无参数 `/summary`“保存报告正文并使用版本号避免覆盖”的归档用途，不再发起一次模型整理请求。报告须包含审查区间、完成时间、审查是否完成、实际验证结果及限制。环境阻断导致的部分审查也可归档，但明确标记部分完成，不能据此宣称全量检查通过。

`/summary` 是 Pi 扩展命令，Codex 或普通文件工具不能直接把它作为工具调用。在 Pi 中，用户仍可在最终报告后手动执行 `/summary` 另存最近回复；无法实际执行命令的宿主直接写入上述报告文件即可，不宣称调用了 `/summary`，也不为保存报告启动新的 Pi 或模型进程。

手动调用允许对同一版本重新审查；“版本未变即跳过”的判断由外部版本监测任务承担。自动化只有在报告确已保存并完成其审查要求后，才能推进自己的已审版本基线。

## 必须保留的判断原则

- “目前是这样”是观测结果；“应永远这样”需要需求或契约依据。
- 先检查原生是否已经承担这项职责，再设计新的补偿或版本判断。
- 测试既验证实现，也携带旧假设；失败本身不决定应该改插件还是改测试。
- 优先公开 API 和原生默认行为；独特用户需求、计费口径与安全边界仍须逐项保留。
- 只根据本轮检查汇报结论。历史报告可提供线索，不能代替本次状态与全量验证。
